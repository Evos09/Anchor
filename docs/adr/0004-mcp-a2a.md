# ADR-0004: MCP and A2A spec versions and SDKs (§17 Q4)

- Status: Accepted
- Date: 2026-10-06

## Context

The Coordination Hub (Phase 4) exposes MCP and A2A endpoints. The spec says
to verify current spec versions and SDK maturity before choosing.

## Pinned versions and how they were verified

- **MCP 2026-07-28**, the current stable revision. Verified from
  `modelcontextprotocol/modelcontextprotocol`: `schema/2026-07-28/schema.ts`
  (`LATEST_PROTOCOL_VERSION = "2026-07-28"`) and the docs site's navigation,
  which marks it "(latest)". This revision is **stateless**:
  - there is no `initialize`;
  - every request carries its protocol version and client capabilities in
    `_meta`;
  - every result carries `resultType`.
- **A2A 1.0**. Pinned from `a2aproject/A2A`: the CHANGELOG lists 1.0.0
  (2026-03-12) and 1.0.1 (2026-05-26), and the specification defines the
  JSON-RPC binding, the `A2A-Version` header and the agent card.

## Decision

Both servers are implemented from the specifications in `anchor-hub`
(`mcp.rs`, `a2a.rs`), on a small synchronous HTTP/1.1 server (`http.rs`).

- **`rmcp` 3.5.1 was evaluated and not adopted** (the user's decision). It
  is official (the MCP organisation's Rust SDK) and supports 2026-07-28,
  but it requires tokio. That would make the trusted backend async and add
  about 15 crates to the audited surface for a small, stateless subset.
  The five-step record is in `docs/deps/dependency-records.md`.
- **No third-party A2A crate exists that is official**; none is used.

### Implemented subset

| Protocol | Implemented | Not implemented |
|---|---|---|
| MCP | Streamable HTTP, `POST /mcp`, JSON responses; `server/discover`, `tools/list`, `tools/call` with `structuredContent` and `isError` results | SSE responses, `subscriptions/listen`, multi round-trip requests, the tasks extension, resources, prompts, and the deprecated sampling, roots and logging |
| A2A | JSON-RPC binding at `POST /a2a`: `SendMessage`, `GetTask`, `ListTasks`; agent card at `GET /.well-known/agent-card.json` | streaming, push notifications, cancellation and the extended card (all answer `UnsupportedOperationError`, -32004, and the card says so) |

### Protocol-level validation

- **MCP**:
  - The `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers must
    match the body (-32020).
  - An unsupported or missing version gets -32022 with `{supported,
    requested}`.
  - An unknown method gets 404 with -32601.
- **A2A**:
  - `A2A-Version` must be `1.0`. An empty header means 0.3 and is answered
    with -32009.
  - The sender of a message is always the agent the bearer token belongs
    to. A `contextId` of `agent:<id>` or `room:<name>` addresses the Hub's
    bus.

## Deviation from §6.5: transport

§6.5 asks for a local-only transport with authentication even locally. A
Unix socket or named pipe cannot carry MCP's Streamable HTTP or A2A's HTTP
bindings to ordinary clients. The Hub therefore listens on **TCP loopback
only (127.0.0.1)**, with these defences:

- a per-agent bearer token on every request except the public agent card:
  32 random bytes, shown once, stored as SHA-256;
- `Host` must name the loopback listener;
- any `Origin` header is refused (DNS rebinding);
- bounded headers and bodies, a total per-request deadline (slowloris),
  and a bounded worker pool.

Refusals are audited. Tests: `anchor-hub/tests/endpoints.rs`.
